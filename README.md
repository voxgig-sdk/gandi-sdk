# Gandi SDK

Gandi API client, generated from an OpenAPI definition constructed from Gandi's API documentation.

Gandi's v5 API manages domain names, LiveDNS zones, SSL certificates, ACME subscriptions, mailboxes, web hosting and organizations at Gandi, the domain registrar and host.

Learn more about Gandi API at [www.gandi.net](https://www.gandi.net).

This is an unofficial SDK for the Gandi public API, generated by Voxgig with [`@voxgig/sdkgen`](https://github.com/voxgig/sdkgen). It is not affiliated with, endorsed by, or sponsored by the upstream API provider.

Learn more about Voxgig SDKs at [voxgig.com/sdk](https://voxgig.com/sdk/).

Full documentation for this SDK: [https://voxgig-sdk.github.io/gandi-sdk/](https://voxgig-sdk.github.io/gandi-sdk/)

> TypeScript, Python, PHP, Golang, Ruby, Lua SDKs, a CLI with an interactive REPL, and an MCP server for AI agents — all generated from one OpenAPI spec by [@voxgig/sdkgen](https://github.com/voxgig/sdkgen).

## About Gandi API

**Credentials.** Every call takes a Gandi Personal Access Token, which starts `pat_`.
Create one in the Organizations section of Gandi's admin site (admin.gandi.net). Pass it as
the `apikey` option and the SDK sends it as `Authorization: Bearer <token>`. The base URL
is `https://api.gandi.net/v5`; to work against Gandi's sandbox, which has its own accounts
and tokens, pass `base: 'https://api.sandbox.gandi.net/v5'`. The CLI and the MCP server read
the token from `GANDI_APIKEY`, so an agent's MCP config sets it under `env`:
`"env": { "GANDI_APIKEY": "pat_..." }`.

```ts
import { GandiSDK } from '@voxgig-sdk/gandi-sdk'

const client = new GandiSDK({ apikey: process.env.GANDI_APIKEY ?? '' })

// Your domains.
const domains = await client.Domain().list()
for (const domain of domains) {
  console.log(domain.data().fqdn)
}

// The DNS records of one of them, on LiveDNS.
const records = await client.LivednsRecord().list({ fqdn: 'example.com' })
console.log(records.length)

// A new A record for www.
await client.LivednsRecord().create({
  fqdn: 'example.com',
  rrset_name: 'www',
  rrset_type: 'A',
  rrset_ttl: 300,
  rrset_values: ['192.0.2.1'],
})
```

**Names.** A domain is named by its `fqdn` throughout: `Domain().load({ fqdn })`,
`LivednsDomain().load({ fqdn })`. The resources below a domain at the registry take
Gandi's own `domain` parameter, as in `DomainHost().list({ domain })`. A DNS record is
named by `fqdn`, `rrset_name` and `rrset_type`, a mailbox by its `address`.

**Actions.** A verb on a resource is an action, selected with `$action` in the request data.
Resetting a domain's authorization code is `$action: 'authinfo'` on a `Domain` update, and
`autorenew`, `status` (the transfer lock), `reachability`, `renew`, `restore` and
`transferout` work the same way. Operations on a whole collection are always actions, so that
leaving a parameter out can never select them: replacing or deleting every record of a zone is
`$action: 'records'` on `LivednsDomain`, every record of one name is `$action: 'name'` on
`LivednsRecord`, and renewing every mailbox of a domain in the Email API is
`$action: 'renew_all'`.

**Scope.** Every one of the 221 operations in the twelve sections of Gandi's v5 documentation
is here, as 60 entities named after Gandi's own resources. The Email API, which Gandi marks
deprecated, is included as `Email*`; its replacement is `Mailbox*`. Some operations cost
money (registering, renewing or transferring a domain, buying a mailbox or a certificate), as
Gandi's documentation warns. For what each field means, follow the links to Gandi's
documentation.

**Not yet run against Gandi.** Gandi publishes no OpenAPI definition, so this SDK's was
constructed from Gandi's API documentation (`.sdk/def/README.md`). Every example in that
documentation was checked against it, but no request has yet been sent to Gandi's API.

## Entities, not endpoints

This SDK exposes the API as **60 semantic entities** that you
call directly, instead of assembling URL paths and query strings. See the [Entities](#entities) table below for the full list. Entities are
**Capitalised** to mark them as the primary surface, each with the operations they
support (`list`, `load`, `create`, `update`, `patch`, `remove`):

```ts
const client = new GandiSDK()
const accesstoken = await client.AccessToken().create({
  expires_at: 'example',
  name: 'example',
})
```

Thinking in entities keeps the mental model small — for people and AI agents alike —
rather than reasoning about raw HTTP routes and query parameters.

## Offline unit testing

Every SDK ships a built-in **test mode** that swaps the HTTP transport for
an in-memory mock, so your unit tests run fully offline — no server, no
network, and no credentials:

### TypeScript

```ts
// The offline mock starts EMPTY — seed it with the records the test needs.
// Shape: { entity: { <entity-name>: { <id>: <record> } } }
const client = GandiSDK.test({
  entity: {
    livedns_domain: {
      test01: { id: 'test01', fqdn: 'example_fqdn' },
    },
  },
})
const livednsdomains = await client.LivednsDomain().list()
// livednsdomains is an array of LivednsDomain entities, one per mock record
console.log(livednsdomains.map((livednsdomain) => livednsdomain.data()))
```

### Python

```python
client = GandiSDK.test()
livednsdomains = client.LivednsDomain().list()
print([item.data_get() for item in livednsdomains])
```

### PHP

```php
// Seed fixture data so offline calls resolve without a live server.
$client = GandiSDK::test([
    "entity" => ["livedns_domain" => ["test01" => []]],

```

## Use it from an AI agent (MCP)

The generated MCP server exposes this SDK's list and load operations as
[MCP](https://modelcontextprotocol.io) tools that Claude, Cursor or Cline
can call directly. It only reads: create, update, patch and remove become tools when the SDK's model sets
`main: kit: target: 'go-mcp': tool: write: true`. Build and register it:

```bash
cd go-mcp && go build -o gandi-mcp .
```

Then add it to your agent's MCP config (Claude Desktop, Cursor, etc.):

```json
{
  "mcpServers": {
    "gandi": {
      "command": "/abs/path/to/gandi-mcp"
    }
  }
}
```

## Direct and prepare

For endpoints the entity model doesn't cover, use the low-level methods:

- **`direct(fetchargs)`** — build and send an HTTP request in one step.
- **`prepare(fetchargs)`** — build the request without sending it.

Both accept a map with `path`, `method`, `params`, `query`,
`headers`, and `body`. See the [How-to guides](#how-to-guides) below.

## Advanced

> Everyday use only needs the sections above. This explains the internals
> behind every call — relevant when writing custom features.

Every SDK call runs the same five-stage pipeline:

1. **Point** — resolve the API endpoint from the operation definition.
2. **Spec** — build the HTTP specification (URL, method, headers, body).
3. **Request** — send the HTTP request.
4. **Response** — receive and parse the response.
5. **Result** — extract the result data for the caller.

A feature hook fires at each stage (e.g. `PrePoint`, `PreSpec`,
`PreRequest`), so features can inspect or modify the pipeline without
forking the SDK.

## Customizing this SDK

This repository contains its own generator (`.sdk/`), so the SDK is
customizable without forking any upstream tool:

- **The model** (`.sdk/model/`) is what generation reads: the API's
  entities and operations, the targets, the features, and this project's
  own settings. It is written in [aontu](https://aontu.dev), a JSON-based
  specification language designed for building ontologies: easy to edit
  by hand, and files unify rather than override, so small declarations
  compose into one model. Regeneration re-reads it every time.
- **Templates** (`.sdk/tm/`) and **components** (`.sdk/src/cmp/`) are
  the two layers of generation, copied into this repo: templates are the
  literal per-language source, components generate the API-shaped parts.
- **Regeneration overwrites.** Each run rewrites every generated file from
  the model, the templates and the components, so an edit made to
  generated output is lost. Say what this project needs in its own model
  (`.sdk/model/project.aontu`), or extend a target with a component of its
  own in `.sdk/src/cmp/<target>/`, registered with `registerComponent`,
  which `voxgig-sdkgen doctor` reports as an addition rather than drift.
- **Customise in `.sdk`.** Edit the templates and components first. When
  they cannot express a change, write a feature of this project's own, or
  an entire custom target, in `.sdk/model/`, `.sdk/tm/` and
  `.sdk/src/cmp/`, and add it by name (`voxgig-sdkgen feature add`,
  `voxgig-sdkgen target add`). This repository regenerates `.sdk` in full
  (`main: kit: copies: 'overwrite'`): set it to `'merge'` before
  customising, so that an add merges toolchain updates into the edited
  copies.

### Project map

| Path | What it holds | Edit it? |
| --- | --- | --- |
| `.sdk/model/project.aontu` | This project's own decisions: package names, versions, features and per-target settings | Yes. The scaffold writes it once and never again. |
| `.sdk/model/text.aontu` | The README wording, in `main.kit.text`: the tagline, the summary and the entity descriptions | Yes. The scaffold writes it once and never again. |
| `.sdk/model/guide/guide.aontu` | How the spec's paths map onto entities and operations | Yes. The scaffold writes it once and never again. |
| `.sdk/model/`, the rest | The API model built from the spec, and the target and feature definitions | Not by hand. Generation, `target add` and a new scaffold run rewrite it, apart from a feature or target this project defines itself. |
| `.sdk/def/` | The OpenAPI spec | Replace it when the API changes. Generation rebuilds the model from it. |
| `.sdk/src/cmp/<target>/`, `.sdk/tm/<target>/` | The components and templates that generate each target | Only after setting `copies` to `'merge'`. This repository regenerates them in full. |
| `.sdk/test/` | The shared test cases the generated tests run | No. |
| `<target>/`, such as `ts/` | One generated SDK per target, with its own tests | No. Generation overwrites it. |
| `README.md`, `LICENSE`, `Makefile` and the other root files | The repository's generated files | No. Generation overwrites them. |
